\section{The thing we are building}
% ===========================================================================

A system that lets a group of people vote and gives two guarantees that
look like they contradict each other:

\begin{itemize}[leftmargin=*]
  \item \textbf{Nobody knows how you voted.} Not the organisers, not the
    miners, not anyone who reads the public record.
  \item \textbf{Anyone can verify the count}, and in particular that no
    voter voted twice.
\end{itemize}

\noindent
The system makes \emph{each ballot} look like a sealed envelope: you can
check that a legitimate voter signed it, but not which one. The pile of
envelopes can be tallied by anyone. The primitive behind it is a
\emph{one-time traceable ring signature} (Scafuro and Zhang~\cite{SZ21},
\cref{sec:otrs}): a key may sign once and stays anonymous; if it signs a
second time, \emph{anything}, everybody learns which key it was.

The project uses that on a chain with money: when a voter registers, a
deposit is locked; if its key is ever exposed, the chain burns the
deposit. Nobody has to judge anybody, because the evidence is two valid
signatures that anyone can check. The pieces:

\begin{enumerate}[leftmargin=*]
  \item The primitive (\file{otrs/}, about 750 lines of Python).
  \item The election logic: poll records and key labels, group assignment,
    classification (\file{voting/}).
  \item The chain (\file{chain/}): a proof-of-work blockchain whose
    validation rules \emph{are} the voting protocol: deposits, groups drawn
    from a block hash, key transfers between rounds, tally and settlement.
  \item A comparison scheme (\file{fs07/}): the Fujisaki--Suzuki traceable
    ring signature~\cite{FS07} that the 2021--22 prototype implemented, with
    its bugs fixed, used only to measure what the one-time scheme costs.
\end{enumerate}

\paragraph{Concrete scale.} Tens to a few thousand voters (councils,
unions, associations, small parties). Not nation-scale.

\section{Cryptographic toolkit}
\label{sec:toolkit}
% ===========================================================================

\subsection{Hash functions}

A \emph{hash function} maps any input to a fixed-size output. We use
SHA-256 (32 bytes) and SHAKE256, which is the same family as SHA-3 but
produces as many output bytes as you ask for.

\begin{intuition}
A fingerprint. Two different inputs almost certainly produce two
different fingerprints. Given a fingerprint, you cannot recover the input.
\end{intuition}

\noindent
Three properties: \textbf{deterministic}; \textbf{collision-resistant}
(nobody can find $x \ne y$ with $H(x) = H(y)$); \textbf{one-way} (given
$H(x)$ you cannot find $x$, or any other preimage, except by guessing).

\paragraph{Random oracles.} Security proofs often pretend that a hash is a
\emph{random oracle}: a box that answers every new question with fresh
random bits and repeats its answer to old questions. Real hashes are not
random oracles, but no attack is known that exploits the difference for
well-designed schemes, and the model makes proofs tractable.
Everything in our signature scheme is a random oracle; there is no other
assumption.

\paragraph{Domain separation.} We use SHAKE256 for several different
oracles. To make them independent, each one starts by absorbing its own
prefix, e.g.\ \texttt{SZ21-OTRS-SHAKE256-v1/L128/G/}. Two oracles with
different prefixes behave like unrelated functions.

\paragraph{Pseudorandom generator.} A function $\Gf : \bits^\lambda \to
\bits^{3\lambda}$ that stretches a short random \emph{seed} into a longer
string that looks random. Here $\lambda$ is the \emph{security parameter}:
128 or 256. We build $\Gf$ from SHAKE256.

\subsection{XOR}

$a \oplus b$ is bitwise exclusive or. Three facts are used constantly:
$a \oplus a = 0$, $a \oplus 0 = a$, and $(a \oplus b) \oplus b = a$. XOR
with a random string hides a value perfectly (one-time pad).

\subsection{Commitments}
\label{sec:commit}

A \emph{commitment} lets you fix a value now and reveal it later.

\begin{intuition}
A sealed envelope on the table. Once it is there you cannot change what is
inside (\emph{binding}), and nobody can read it until you open it
(\emph{hiding}).
\end{intuition}

\paragraph{Naor's bit commitment~\cite{Naor91}.} The receiver picks a random
string $\rho$ of $3\lambda$ bits. To commit to a bit $b$, the sender picks
a seed $r$ and sends
\[ c = \Gf(r) \oplus b\cdot\rho \qquad(\text{that is, } \Gf(r)
\text{ if } b = 0,\ \Gf(r) \oplus \rho \text{ if } b = 1). \]
To open it, the sender reveals $(b, r)$ and the receiver recomputes $c$.
\begin{itemize}[leftmargin=*]
\item \textbf{Hiding}: $\Gf(r)$ looks random, so $c$ says nothing about $b$.
\item \textbf{Binding}: to open $c$ both ways you need $r_0, r_1$ with
      $\Gf(r_0) = \Gf(r_1) \oplus \rho$, i.e.\ $\Gf(r_0) \oplus \Gf(r_1)
      = \rho$. There are $2^{2\lambda}$ pairs of seeds but $2^{3\lambda}$
      possible $\rho$, so for a random $\rho$ such a pair almost surely
      does not exist.
\end{itemize}

\paragraph{Equivocal mode: the trapdoor.} Now let the \emph{sender} build
$\rho$ itself, from two seeds:
\[ \rho = \Gf(s^0) \oplus \Gf(s^1). \]
It looks exactly as random as before. But now the sender can commit with
$c = \Gf(s^0)$ and decide \emph{later} which bit it was: open as $0$ with
$s^0$ (since $c = \Gf(s^0)$), or as $1$ with $s^1$ (since $\Gf(s^1) \oplus
\rho = \Gf(s^0) = c$).

\begin{intuition}
An envelope with a false bottom that only its maker knows about. The key
observation of the whole project: if the maker opens the \emph{same}
envelope once as $0$ and once as $1$, it has shown both $s^0$ and $s^1$,
and anybody can check that $\Gf(s^0) \oplus \Gf(s^1) = \rho$. The false
bottom is exposed, and so is whoever made it.
\end{intuition}

\subsection{Digital signatures}

A digital signature proves that a message was endorsed by the holder of a
secret key: $\KeyGen() \to (\sk, \pk)$, $\Sign(\sk, m) \to \sigma$,
$\Verify(\pk, m, \sigma) \to$ true/false.

We use \textbf{Ed25519} for every signature where identity \emph{is}
supposed to be visible: accounts that pay, sponsors that register voters,
creators that open polls. Voters do not use it for ballots.

\subsection{Ring signatures}
\label{sec:ringsigs}

A \emph{ring signature}~\cite{RST01} is signed with one secret key and
verified against a list of public keys, the \emph{ring}. It proves ``one of
these people signed'' and hides which one.

\begin{intuition}
A room of people behind a curtain. A note comes out under the curtain. You
can check that it came from someone in the room, but not from whom.
\end{intuition}

\noindent
For voting this is half of what we need. The other half is stopping a
voter from slipping two notes under the curtain. There are three
flavours:

\begin{center}
\small
\begin{tabularx}{\textwidth}{l X X}
\toprule
Flavour & Two signatures by one key \ldots & Consequence \\
\midrule
plain & look unrelated & a voter can vote as often as it likes \\
linkable~\cite{LWW04} & are recognisably linked & the second ballot is discarded; the voter stays anonymous; trying is free \\
traceable~\cite{FS07} & on different messages (same tag), reveal the key & the voter is exposed; can be punished \\
one-time traceable~\cite{SZ21} & \emph{any} two, reveal the key & as above, and the rule is simply ``each key signs once'' \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
The one-time flavour matches a poll exactly. It also has a property the
others lack in practice: it is built from a hash function alone, so a
quantum computer does not break its anonymity (\cref{sec:fs07}).

% ===========================================================================
\section{The one-time traceable ring signature}
\label{sec:otrs}
% ===========================================================================

\subsection{The idea in one paragraph}

A public key is a list of $\lambda$ trapdoored Naor strings $\pk_1, \ldots,
\pk_\lambda$ (\cref{sec:commit}). To sign, every ring member gets a
$\lambda$-bit string $x_i$, committed bit by bit; the signature is valid if
the XOR of all $x_i$ equals a hash $z$ of everything committed. The
signer can fake its commitments because it holds the trapdoors: it
commits first, learns $z$, and then opens its own commitments to whatever
$x_l$ makes the XOR work out. Everybody else's commitments were opened
honestly. A verifier sees $N$ correctly opened commitments and cannot tell
which ones were faked. But each faked opening reveals one of the two seeds
of a row, and a second signature, with a different $z$, will need some row
opened the other way: both seeds are out, and the row names its key.

\subsection{The scheme}
\label{sec:otrs-scheme}

Notation: $\lambda$ the security parameter, $N$ the ring size, rows
indexed by $j = 1..\lambda$, ring members by $i = 1..N$, the signer at
position $l$.

\paragraph{\KeyGen.} Pick $2\lambda$ seeds $s^0_j, s^1_j$ of $\lambda$
bits. Publish $\pk_j = \Gf(s^0_j) \oplus \Gf(s^1_j)$ for $j = 1..\lambda$.
At $\lambda = 128$ that is 128 rows of 48 bytes: 6\,144 bytes.

\paragraph{\Sign$(\sk_l, R, m, \ctx)$.}
\begin{lstlisting}[style=pseudo]
for every member i $\ne$ l:
    $x_i$ $\sample$ $\{0,1\}^\lambda$                       # its random share
    for j in 1..$\lambda$:  $r_{i,j}$ $\sample$ seed;  $c_{i,j}$ = G($r_{i,j}$) $\oplus$ $x_i[j]\cdot\pk_{i,j}$
for j in 1..$\lambda$:      $c_{l,j}$ = G($s^0_{l,j}$)            # signer: undecided
z  = H($\ctx$, R, m, all $c_{i,j}$)                  # the target
$x_l$ = z $\oplus$ $\bigoplus_{i\ne l} x_i$                       # signer's share, forced
for j in 1..$\lambda$:      $r_{l,j}$ = $s^{x_l[j]}_{l,j}$             # open as needed
output  ($x_1, \ldots, x_N$,  all $r_{i,j}$)              # $N\lambda(\lambda+1)$ bits
\end{lstlisting}

\paragraph{\Verify.} Recompute every $c_{i,j} = \Gf(r_{i,j}) \oplus
x_i[j]\cdot\pk_{i,j}$ (it works for the signer too, by the equivocation
trick), recompute $z$ and check $\bigoplus_i x_i = z$.

\paragraph{\Trace.} Given two valid signatures with seeds $\alpha_{i,j}$
and $\beta_{i,j}$ on the same ring: member $i$ is traced if, for some row
$j$, $\Gf(\alpha_{i,j}) \oplus \Gf(\beta_{i,j}) = \pk_{i,j}$.

\subsection{A worked example}

Take $N = 2$, Alice at position 1, Bob at position 2, Alice signs. Pretend
$\lambda = 3$ (in reality it is 128).
\begin{enumerate}[leftmargin=*]
\item Bob's share: Alice picks $x_2 = 101$ and seeds $r_{2,1}, r_{2,2},
      r_{2,3}$, and computes $c_{2,1} = \Gf(r_{2,1}) \oplus \pk_{2,1}$,
      $c_{2,2} = \Gf(r_{2,2})$, $c_{2,3} = \Gf(r_{2,3}) \oplus \pk_{2,3}$:
      honest Naor commitments to $1, 0, 1$ under Bob's rows.
\item Her own: $c_{1,j} = \Gf(s^0_{1,j})$ for $j = 1, 2, 3$.
\item $z = \Hf(\ldots) = 110$, say. Then $x_1 = 110 \oplus 101 = 011$.
\item She opens her rows to $0, 1, 1$: $r_{1,1} = s^0_{1,1}$, $r_{1,2} =
      s^1_{1,2}$, $r_{1,3} = s^1_{1,3}$.
\end{enumerate}
A verifier checks four things it can compute: each commitment from its
opening, $z$ from the commitments, and $011 \oplus 101 = 110$. Both rows
of commitments were opened correctly; nothing marks Alice's as special.

Now Alice signs a second time. The other share is new, so $z'$ is new,
say $x'_1 = 001$. Row 1 is opened with $s^0_{1,1}$ again, but row 2 now
needs $s^0_{1,2}$, and the first signature revealed $s^1_{1,2}$. Anyone
computes $\Gf(s^1_{1,2}) \oplus \Gf(s^0_{1,2}) = \pk_{1,2}$: row 2 of
Alice's key. With $\lambda = 128$ rows, the chance that two random
targets agree on every bit is $2^{-128}$.

\subsection{Why it works}

\paragraph{Anonymity.} For Bob's position the seeds are fresh random
seeds. For Alice's they are her secret seeds, which nobody has seen
before. Both look like random strings of $\lambda$ bits, and the only way
to tell a secret seed from a fresh one is to find which seed hashes to
which half of a row, i.e.\ to invert $\Gf$. This holds as long as Alice
has signed only once: a second signature would put both seeds of some row
in public.

\paragraph{Traceability.} To sign you must open, at some position, a
commitment you made \emph{before} learning $z$, to a value that depends on
$z$. You can only do that at a position whose trapdoor you hold. Two
signatures need two different targets, so at your position the two
openings differ in some row and reveal both seeds. Scafuro and Zhang prove
the stronger \emph{public traceability}: $N$ keys together cannot produce
$N + 1$ valid signatures on one ring without two of them tracing a key.

\paragraph{Exculpability.} To frame Alice you would need both seeds of
one of her rows. Her single signature shows one; the other never leaves
her machine. Copying her signature does not help: a copy is identical and
traces nothing.

\subsection{Same message, still traced}

With a linkable or an FS07 signature, signing the \emph{same} ballot twice
is harmless: the two are linked as a copy. Here, if Alice signs ``yes''
twice with fresh randomness, Bob's share differs, $z$ differs, and she is
traced. This is the rule ``a key signs once'' taken literally, and it has a
practical consequence: a wallet that re-signs a ballot because a broadcast
timed out would cost its user the deposit. Our implementation therefore
derives all the randomness ($x_i$ and the seeds $r_{i,j}$) from the secret
and the full input with SHAKE256. Re-signing the same input gives the same
bytes: a copy, which the chain refuses harmlessly.

\subsection{The zero-row gap}
\label{sec:zerorow}

\begin{flagbox}[Something the paper missed]
If a row $\pk_j$ is all zeros, the commitment $\Gf(r) \oplus b\cdot\pk_j =
\Gf(r)$ is the same for both bits, so \emph{any} seed opens it either way.
A key made entirely of zero rows (which honest-looking key generation
produces if $s^0_j = s^1_j$) can sign as often as it likes, each time with
fresh seeds, and is never traced. The verification algorithm of Fig.~1
in~\cite{SZ21} does not check for this. Our \file{Ring} refuses every key
with a zero row; \file{tests/test\_otrs.py::TestZeroRow} runs the attack
with the check switched off.
\end{flagbox}

\noindent
Why the rows are $3\lambda$ bits and not $\lambda$: for a non-zero row, a
cheater would need two different seed pairs with the same XOR. That is a
4-XOR problem; with $3\lambda$-bit outputs Wagner's
algorithm~\cite{Wagner02} needs about $2^\lambda$ work. Shorter rows would
make it cheap.

\subsection{Sizes and speed}

At $\lambda = 128$ a signature is $N \cdot 129 \cdot 16$ bytes, 2\,064
bytes per ring member, plus 5 bytes of header; at $\lambda = 256$, four
times that. Verification costs $128$ SHAKE calls per member: 0.16~ms in our
Python, 1.3~ms for a ring of 8. A ring of 1\,000 gives 2~MB signatures,
which is why the design never uses one big ring (\cref{sec:groups}).

\subsection{What our implementation adds}

\begin{itemize}[leftmargin=*]
\item \textbf{A label in every key}: 32 public bytes, hashed into the ring.
      The chain uses it to bind a key to its single use
      (\cref{sec:labels}).
\item \textbf{A context string} inside $\Hf$ (poll and round), and a
      short digest of the ring instead of the whole ring.
\item \textbf{A 32-byte master secret} from which the $2\lambda$ seeds are
      derived, so key files are small.
\item \textbf{Deterministic signing} and the \textbf{zero-row check} (above).
\item \textbf{Trace returns every culprit}, because a coalition of keys can
      split the rows it opens.
\item \textbf{Trace from cached openings}: verification already computes
      every $\Gf(r_{i,j})$; we keep them as one big integer, and tracing two
      signatures becomes $A \oplus B \oplus P$ and a search for an all-zero
      row: 0.04~ms for $N = 8$.
\end{itemize}

\begin{lstlisting}[style=py]
from otrs import Ring, keygen
voters = [keygen() for _ in range(8)]
ring = Ring([v.pk for v in voters])
sig = ring.sign(voters[3], b"yes", b"poll-7")
assert ring.verify(sig, b"yes", b"poll-7")
second = ring.sign(voters[3], b"no", b"poll-7")
ring.trace(sig, second).culprits         # (3,)
\end{lstlisting}

\section{The design: deposits, groups and transfers on a chain}
\label{sec:chain}
% ===========================================================================

\subsection{Why a chain}

Somebody has to keep the record of ballots. If that is the organiser, the
organiser can drop ballots or show different records to different
people. A proof-of-work chain lets anybody keep the record: the valid chain
with the most work wins, and every node checks every rule itself. It also
has a currency, which is what makes deposits possible.

\subsection{Blocks and proof of work}

A block has a header $(\mathit{prev\_hash}, \mathit{height},
\mathit{difficulty}, \mathit{timestamp}, \mathit{miner}, \mathit{tx\_root},
\mathit{nonce})$ and a list of transactions. It is valid only if
SHA-256 of the header starts with $\mathit{difficulty}$ zero bits and
$\mathit{difficulty}$ is the value the rule prescribes (one bit up or down
when the median block interval leaves $[30, 90]$ seconds). Nodes follow
the valid chain with the largest $\sum 2^{\mathit{difficulty}}$
(\file{chain/node.py}).

\subsection{Accounts and transactions}

Accounts are Ed25519 keys holding \emph{eVotes}. There are six kinds of
transaction:

\begin{center}
\small
\begin{tabular}{lll}
\toprule
Kind & Signed by & Effect \\
\midrule
\texttt{coinbase}        & ---           & reward + fees to the miner \\
\texttt{transfer}        & sender        & payment \\
\texttt{setup\_poll}     & creator       & opens a poll \\
\texttt{register\_voter} & sponsor       & registers a labelled one-time key; fee + deposit \\
\texttt{ballot}          & one-time key  & a choice, ring-signed in one group \\
\texttt{key\_transfer}   & one-time key  & moves the vote to a fresh key \\
\bottomrule
\end{tabular}
\end{center}

\noindent
Ballots and key transfers carry no account, no fee and no Ed25519
signature, so they do not link a voter to an account.

\subsection{Opening a poll and registering voters}
\label{sec:labels}

The creator fixes options, a schedule (registration close, voting open,
voting close), the group size $k$, the number of rounds, the deposit $D$
and $\lambda$. Before registration closes, a \emph{sponsor} (the voter
itself, the organiser, an association) registers each voter: it signs the
transaction, pays the fee and locks $D$.

\paragraph{Key labels.} The 2022 design had each voter sign its own
registration, to prove it held the key. A one-time key cannot do that:
it would spend its only signature. Instead every key carries a public
label, and the chain accepts a registration only if
\[ \mathit{label} = \mathrm{SHA\text{-}256}(\texttt{e-ring-voting/register-v1}
   \,\|\, \mathit{election\_id} \,\|\, \mathit{len} \,\|\,
   \mathit{handle}). \]
The key was made for this poll and this handle, so a registration copied
from the mempool cannot be filed under another handle or in another poll,
and a key cannot be registered twice. A label does not prove that anybody
holds the key; registering a key nobody holds just creates a voter that
never votes.

\begin{lstlisting}[style=shell]
evote-chain voter-keygen --election-id $EID --handle alice --out alice.json
evote-chain register-voter ... --sponsor org.json --election-id $EID --voter alice.json
\end{lstlisting}

\subsection{Groups from a beacon}
\label{sec:groups}

One ring for everybody would make every ballot $2\,064 \cdot N$ bytes.
Instead, the first block past \emph{voting open} splits the registered keys
into groups of $k$ to $2k - 1$ members. The order is decided by hashing
each key's fingerprint with the \texttt{prev\_hash} of that block, the
\emph{beacon}, which did not exist when registration closed. Neither the
organiser nor a sponsor can therefore place its own keys around a target.
The miner of the beacon block has some influence: it can throw away a block
it does not like, at the cost of the block reward (\cref{sec:assessment}).

\subsection{Rounds: vote or move}

The voting window is split into rounds. In each round, a key spends its one
use on exactly one of:
\begin{itemize}[leftmargin=*]
  \item a \textbf{ballot}: \texttt{ballot-v1}$\,\|\,$choice, signed on its
    group with the round's context;
  \item a \textbf{key transfer} (not in the last round):
    \texttt{key-transfer-v1}$\,\|\,\pk'$, naming a fresh key $\pk'$ labelled
    for the next round. At the end of the round all the new keys are put
    into new groups with a new beacon.
\end{itemize}
A voter who moves hides, in the next round, among \emph{all} members of
every group the keys of its new group came from: roughly $k$ times as
many people. A voter who does both has signed twice and is traced.

\subsection{Admitting messages: the tag book}

Each group has a \emph{tag book} (\file{voting/tally.py}) that keeps the
openings of every recorded signature. A new message that verifies is
traced against all of them:
\begin{center}
\small
\begin{tabular}{lll}
\toprule
Outcome & When & Effect \\
\midrule
replay & byte-identical to a recorded message & invalid \\
fresh & traces nobody & recorded \\
evidence & traces a key not yet exposed & recorded; the key is a culprit \\
saturated & traces only keys already exposed & invalid \\
exhausted & would be the $(N{+}1)$-th untraced signature & invalid (cannot happen) \\
\bottomrule
\end{tabular}
\end{center}
So each key leaves at most two messages on chain, and replays of somebody
else's ballot cannot get in at all.

\subsection{Close and settlement}

At the first block past \emph{voting close}, every node computes, without
any transaction asking it to: the tally of all valid ballots of all
rounds; the culprits (keys used twice, with the handle they were
registered under); the deposits of round-0 culprits, which are
\emph{burned}; and the refunds of every other deposit to its sponsor.
Burned, not paid to the miner: otherwise a miner could register keys,
double-vote with them, and collect.

\subsection{A worked example}

The README runs this poll from the command line in two seconds: six
voters, groups of three, two rounds, deposit 10. \texttt{v1} moves to a
fresh key in round 0 and votes from it in round 1; \texttt{v2} votes twice.
The audit prints:
\begin{lstlisting}[style=shell]
poll 136b50a3f69d8247...  phase=closed  registered=6  groups=[[3, 3], [1]]
  tally: {'no': 2, 'yes': 1}
  key transfers per round: [1, 0]
  key used twice in round 0: handle 'v2' (key b47b7ecb9d398b36...)
  deposits: 10 burned, 50 refunded
\end{lstlisting}
\texttt{v2}'s two ballots are both void, its handle is named and its
sponsor lost 10. The round-1 group has one member, but its ballot hides
among the three members of the group the transfer came from.

\section{Why this scheme, and not the prototype's}
\label{sec:fs07}
% ===========================================================================

The 2021--22 prototype implemented the Fujisaki--Suzuki scheme
(FS07)~\cite{FS07}, which works in a group where discrete logarithms are
hard. A signature there carries $h^{x}$, where $x$ is the signer's secret
key and $h$ a hash of the tag: the same value in every signature by that
key under that tag, which is how a double-sign is detected.

\begin{center}
\small
\begin{tabular}{lll}
\toprule
& FS07 (\file{fs07/}) & SZ21 (\file{otrs/}), $\lambda = 128$ \\
\midrule
Assumption & DDH + random oracle & random oracle \\
Quantum computer & recovers $x$; every past ballot names its signer & none known \\
Same ballot twice & linked, not exposed & exposed \\
Public key & 32 B & 6\,177 B \\
Signature, ring of 8 & 548 B & 16\,517 B \\
Verify, ring of 8 & 2.6 ms & 1.3 ms \\
\bottomrule
\end{tabular}
\end{center}

\noindent
The deciding row is the second. A public chain keeps every ballot forever.
Validity of the signatures only matters until the poll closes, but secrecy
of the ballots must last decades. Once someone has a large quantum
computer, every FS07 ballot ever written to the chain can be opened; the
one-time scheme gives that computer nothing better than guessing seeds.
The price is size: 30 times larger signatures, which groups of 8 to 16
keep at 16 to 33~kB per ballot.

\paragraph{The prototype's bugs.} Its hash into the group returned
$g^{t}$ with $t$ computable from public data, so anyone could compute $h^{x_j}
= \pk_j^{\,t}$ for every member and find the signer: no anonymity at all.
And it inverted the ring position modulo the wrong number, so only position
1 produced verifying signatures. Both passed a demo. The fixed FS07 is kept
in \file{fs07/} for the comparison.

\section{Open problems --- where you would contribute}
\label{sec:open}
% ===========================================================================

\begin{enumerate}[leftmargin=*]
  \item\label{itm:slash} \textbf{Slashing transferred keys.} A key that
    arrived by transfer has no deposit. Can a deposit travel with the
    transfer without linking the new key to the old?
  \item\label{itm:beacon} \textbf{An unbiasable beacon}: a VDF or a
    commit--reveal among sponsors instead of \texttt{prev\_hash}.
  \item\label{itm:pricing} \textbf{Pricing.} Deposits and fees for a given
    $k$ and adversary budget; paying miners to include fee-less ballots.
  \item\label{itm:leak} \textbf{Per-group tallies leak.} Tally across
    groups without publishing per-group counts.
  \item\label{itm:short} \textbf{Shorter signatures.} A hash-based
    one-time traceable scheme sub-linear in $N$ would allow larger groups.
  \item\label{itm:qrom} \textbf{A proof in the quantum random-oracle
    model} for~\cite{SZ21}.
  \item\label{itm:formal} \textbf{Tamarin / ProVerif model} of
    registration, groups, rounds and settlement.
  \item\label{itm:receipt} \textbf{Receipt-freeness.} A voter who reveals
    its master secret lets a coercer recognise its ballot.
    JCJ~\cite{JCJ2005}-style machinery would be needed.
  \item\label{itm:net} \textbf{A network layer} for the chain.
\end{enumerate}

\section{Critical assessment}
\label{sec:assessment}
% ===========================================================================

\subsection{The precise anonymity claim}

\textbf{What we provide.} Given the chain and one ballot signed in group
$g$ by a key used once: no efficient adversary can tell which member of $g$
produced it noticeably better than guessing, in the random-oracle
model~\cite{SZ21}. A ballot cast after a transfer hides among the members
of every origin group of its new group.

\begin{flaw}[The anonymity set is the honest part of the group]
Sybil keys look honest. With half the keys adversarial and $k = 4$, one
honest voter in eight has no honest peer; with $k = 8$, about one in 130.
Choose $k$ against the sybil share you expect.
\end{flaw}

\begin{flaw}[Per-group tallies are public]
A unanimous group reveals everyone in it.
\end{flaw}

\begin{flaw}[Beacon bias]
The miner of the beacon block can discard blocks to redraw groups, at a
block reward each.
\end{flaw}

\begin{flaw}[One use, really]
Anonymity holds only for a key that signs once. The chain makes a second
use impossible to hide, and our signer is deterministic, but a wallet that
reuses a key elsewhere destroys its own anonymity.
\end{flaw}

\begin{flaw}[Network and device]
Submitting a ballot reveals IP and timing; malware with the key signs
anything.
\end{flaw}

\subsection{The precise verifiability and accountability claims}

\textbf{What we provide.} Anyone replaying the chain obtains the same
groups, tally, culprits and settlement; nobody publishes a result that
could differ from it. A culprit's key really signed twice, unless its
secret leaked.

\begin{flaw}[Transferred keys are not punished]
A second use voids their messages; there is no deposit to burn.
\end{flaw}

\begin{flaw}[Censorship]
Ballots pay no fee; a censoring majority of hash power can keep them out
until the round ends.
\end{flaw}

\begin{flaw}[Eligibility is the sponsor's word]
The chain checks labels, not personhood. Sponsors are accountable on chain,
but nothing stops a sponsor from registering keys for people who do not
exist.
\end{flaw}

\subsection{The honest pitch}

\begin{quote}
\itshape
v1.0 makes double-voting cost money without a judge: a one-time traceable
ring signature names any key used twice, and the chain burns its deposit.
The signature needs nothing but a hash function, so ballots stay secret
even against a future quantum computer. Voter groups come from a beacon
nobody controls at registration time, and voters can widen their anonymity
by moving between groups. It does not provide coercion resistance, punish
transferred keys, or remove miner bias from the beacon, and its signatures
are large.
\end{quote}

\appendix
\section{Glossary}
% ===========================================================================

\begin{description}[leftmargin=*,style=nextline]
  \item[anonymity set]
    The keys a ballot could have come from.
  \item[beacon]
    The \texttt{prev\_hash} of the block that freezes a round; it decides
    the groups.
  \item[commitment]
    A sealed value: binding and hiding. Here Naor's bit commitment.
  \item[culprit]
    A key that signed twice in a round; named with its registration
    handle.
  \item[deposit]
    eVotes locked per registered voter; burned if the key is a round-0
    culprit, refunded to the sponsor otherwise.
  \item[equivocal mode]
    A Naor commitment key built from two seeds, which lets its maker open
    a commitment either way.
  \item[fingerprint]
    SHA-256 of an encoded public key; how the chain names keys.
  \item[group]
    A set of $k$..$2k-1$ keys that sign as one ring.
  \item[key label]
    32 public bytes in a key that name its single use.
  \item[key transfer]
    A ring-signed message moving a voter's right to a fresh key for the
    next round.
  \item[$\lambda$]
    The security parameter, 128 or 256.
  \item[one-time]
    Each key signs at most once.
  \item[opening]
    The seed revealed for a commitment.
  \item[random oracle]
    An idealised hash function returning fresh random bits for each new
    input.
  \item[round]
    A slice of the voting window with its own context and groups.
  \item[row]
    One of the $\lambda$ Naor strings of a public key.
  \item[sponsor]
    The account that pays a voter's registration fee and deposit.
  \item[tag book]
    Per-group record of signatures and their openings; decides replay,
    fresh, evidence, saturated.
  \item[target]
    $z = \Hf(\ldots)$, the value every signature's shares must XOR to.
  \item[trace]
    Finding a row whose two seeds appear in two signatures.
\end{description}
